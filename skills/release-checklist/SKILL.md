# 发版编排

## Overview

本项目的核心矛盾：**改 `index.html` 就自动意味着要发版**，但发版牵动版本号、回归测试、速览文案、推送验收一长串动作。
这个技能不做具体操作，只负责**按正确顺序把 `bump-version` / `run-regression` / `push-github` 串起来**，并在每个决策点停下来问。

## When to Use

- 功能/界面代码改完，准备发布
- 不确定"这次要不要跟版"
- 想一次走完发版流程，不漏步骤
- 上一次发版漏了东西（页面版本不对、缓存不刷新）

## Process

**步骤 0：先定「这次发不发版」——这是硬门槛**

改动分两类，处理方式相反：

| 改动性质 | 要不要发版 | 例子 |
|---|---|---|
| `index.html` 的功能 / 界面 / 数据逻辑 | **发** | 新增模块、修 bug、改交互 |
| 纯文档、纯注释、`portal/` 独立页（不影响主包） | **不发** | 改 AGENTS.md、改 README |

**定下来再动手。** 发版的代价是版本号 + 一堆断言要跟，写了就要面对；不发版的改动绝不要去碰版本号。

**步骤 1：确认版本号现状**

```bash
cur=$(grep -o "class-manager-v[0-9.]*" sw.js | head -1 | sed 's/class-manager-v//')
echo "当前：$cur"
```

新版本号按语义定：功能新增 `+0.0.1` 位（如 3.9.23 → 3.9.24），大改动升次版本位。

**步骤 2：改代码**

只改必要的地方。本项目是单文件 SPA，`index.html` 是唯一功能改动文件（零框架零构建）。

**步骤 3：跟版**

调用 `bump-version` 技能。**注意**：`AGENTS.md` §6 里"版本号三处"的说法是 v2.18 时代的，已经过时——实际落点含 `sw.js` 的 `?v=` 预缓存参数、`apple-touch-icon`、速览标题与正文。以 `grep` 结果为准。

**步骤 4：写速览**

`index.html` 里 `📝 近版更新速览` 加一条。惯例：emoji 小图标开头 + **加粗的版本标题** + 一句人话说明。旧条目保留。

**步骤 5：跑回归**

调用 `run-regression` 技能。`FAIL: none` 才继续。

**步骤 6：推送**

调用 `push-github` 技能。

**步骤 7：验收**

- blob sha 变了（`push-github` 的 Verification）
- Pages 线上页面拿到新版本
- 页面三处可见版本标记一致

**步骤 8：记录**

在 `PROGRESS.md` **文末**追加本版章节。⚠️ 该文件开头的「当前状态速览 / 待办队列」等章节是 v2.8.0 期的化石，**不要往那里写**，也不要信那里的数字。

## Rationalizations

| 借口 | 反驳 |
|---|---|
| "先发出去，速览回头补" | 一定不会补。而且速览是用户看新功能的唯一入口 |
| "版本号我手动改几处就行" | 漏一个 `?v=` 就缓存不刷新，用户抱怨"改了没效果" |
| "测试太慢，这次跳过" | 单文件 SPA 一处改动波及面极大。跳过回归省下的时间，会在线上以十倍代价还回来 |
| "PROGRESS 开头那段更新一下" | 那是化石区。写进去会被下一个人当成现状 |
| "文档改动也算发版吧，一起走了" | 发版有成本。纯文档改动不碰版本号，省一轮全套动作 |

## Red Flags

- 没定"发不发版"就开始改版本号
- 速览只加了标题没加说明，或说明里出现"当前版本"自指矛盾
- 回归没跑完就推送
- 往 `PROGRESS.md` 开头那几节写东西
- 推送后没验收就宣布完成

## Verification

一次发版算完成，必须同时有：

1. `sw.js` 的 `CACHE_NAME` 是新版本
2. `node _runall.js` → `FAIL: none`
3. `index.html` 的 blob sha 已变
4. 线上页面三处版本标记一致且为新版本
5. 速览里有本次的条目
6. `PROGRESS.md` 文末有本版记录
